## `refine a11y` — contrast, focus, and what the archetype owes a screen reader

The fourth gate section. The three before it ask whether the component was
specified, whether it was built out of what was specified, and whether the names
are on the scale. This one asks the first question about the people who will use
the thing: **can it be seen, can it be reached with a keyboard, and does it tell
assistive technology what it is?**

| Property | Value |
|----------|-------|
| mode | `refine a11y` |
| implemented in | `lib/refine-a11y.js` |
| reads | the recorded colour tokens, the component spec blocks, and the markup a component was adopted into |
| writes | nothing — a mode returns its section and no report |
| kind | deterministic; the arithmetic is WCAG's and the expectations are the table below |

`refs/refine/protocol-refine.md` §1 calls this the one mixed section, and that is
still the honest description of the *question*. The implementation narrows it on
purpose: **every judgement this mode makes is bounded by a table in this file.**
A contrast ratio is arithmetic. A focus state is present or it is not. An ARIA
expectation is a row, and an archetype with no row is reported as having no row
rather than graded against an opinion.

---

### What it can say, and what it cannot

Three sentences are attached to every result rather than footnoted, because each
one bounds a check that would otherwise read as stronger than it is.

- **Contrast is measured on recorded values, not on rendered pixels.** The
  numbers come from `DESIGN-SYSTEM.md`. A component whose real background is set
  by a parent, a theme or a media query is measured against what the spec says,
  which is the only thing the design system knows.
- **Keyboard behaviour is stated, never checked.** Whether `Space` toggles a
  switch is a fact about a running program. This mode reads text, so it names
  the expectation and says it was not verified.
- **A pairing nobody recorded is not invented.** Two colour tokens are checked
  against each other only where a component spec binds both. Every token against
  every other token would produce a wall of ratios about pairs no screen will
  ever show together.

---

## 1. Contrast

### Where a pair comes from

`DESIGN-SYSTEM.md` records colours one at a time. It does not record that
`text-primary` is meant to sit on `surface-default` — nothing in the token table
carries that fact. The component spec does: a spec block that fills both a
foreground slot and its background slot has stated a pairing, and that statement
is the only evidence this section will act on.

<!-- phyllum:a11y-pairs -->

| Foreground slot | Background slot | Context | The pair it names |
|-----------------|-----------------|---------|-------------------|
| `text-colour` | `background` | normal-text | the component's own label on its own surface |
| `border-colour` | `background` | ui-component | the visible boundary of the control |
| `indicator-colour` | `background` | ui-component | the mark that says *checked* — a tick, a dot |
| `indicator-colour` | `track-colour` | ui-component | a progress fill against the rail it runs in |
| `thumb-colour` | `track-colour` | ui-component | a switch's moving part against its rail |
| `focus-ring` | `background` | ui-component | a ring that cannot be seen is not a focus state |

A state that overrides one side of a pair makes a second pair. `hover:` with its
own `background` is re-checked against the same `text-colour`, because a hover
that drops a label below the bar is a failure a user meets by moving the mouse.

A colour token no spec binds on either side is reported **unpaired**. That is a
`warn` and it is one finding for the whole set, not one per token: it is a
question about what the system has recorded, not a fault in any one colour.

### The thresholds

<!-- phyllum:a11y-contrast -->

| Context | Minimum ratio | Applies to |
|---------|---------------|------------|
| normal-text | 4.5 | text below 24px, or below 18.66px when it is bold — WCAG 2.x 1.4.3 |
| large-text | 3 | text at 24px and above, or 18.66px and above when bold — WCAG 2.x 1.4.3 |
| ui-component | 3 | borders, indicators, focus rings and other non-text boundaries — WCAG 2.x 1.4.11 |

The ratio is WCAG's: relative luminance from linearised sRGB channels, then
`(lighter + 0.05) / (darker + 0.05)`, so black on white is 21 and a colour on
itself is 1. It is implemented in `lib/refine-a11y.js` and nowhere else.

Which of the first two rows applies to a text pair is read from the component's
own `typography` token — its size, and its weight for the bold cut-off. A
component that records no typography token is measured at **normal-text**, the
stricter bar, because the alternative is granting a discount nothing recorded.

### What cannot be measured

A slot bound to something that is not a colour Phyllum can read — a `TODO`, a
gradient, a name no token table records — is `unreadable-pair`, a `warn`. So is
a pair where either side is translucent: the real ratio then depends on whatever
is behind it, which the design system does not record. Composing an answer out
of an assumed backdrop would be inventing the input.

## 2. Focus states

An interactive component that gives no visible sign of keyboard focus is
unusable by keyboard, and the loss is silent — nothing errors, the ring simply
is not there.

A component of an interactive archetype passes when its spec records a focus
treatment: a `focus` entry under `states:`, or a `focus-ring` slot under
`properties:`. Either is enough. Neither is `focus-missing`, an `error`.

This is deliberately stricter than `create`'s contract, and the difference is
worth naming rather than discovering. `refs/create/archetypes.md` makes `focus` a
mandatory state for `Input`, `Select`, `Toggle`, `Checkbox` and `Radio`, and it
does **not** for `Button`, `Link`, `Modal` or `Tabs`. `create` asks what a spec
must contain to be a spec; the gate asks what a component must have to ship, and
a button with no focus ring does not ship. A `Button` spec that names no focus
treatment therefore passes `create` and fails here, on purpose.

Which archetypes are interactive is the `Interactive` column of the table below,
so there is one list and not two.

## 3. ARIA expectations, per archetype

<!-- phyllum:a11y-aria -->

| Archetype | Interactive | Native element | Role | Attributes | Keyboard |
|-----------|-------------|----------------|------|------------|----------|
| Button | yes | `button` | `button` | — | `Enter` and `Space` activate it |
| Input | yes | `input` | `textbox` | — | it takes text; `Tab` moves off it |
| Card | no | `div` | — | — | — |
| Badge | no | `span` | — | — | — |
| Modal | yes | `dialog` | `dialog` | `aria-modal`, `aria-labelledby` | `Esc` closes it; focus stays inside while it is open |
| Toggle | yes | `button` | `switch` | `aria-checked` | `Space` toggles it |
| Checkbox | yes | `input` | `checkbox` | `aria-checked` | `Space` toggles it |
| Radio | yes | `input` | `radio` | `aria-checked` | the arrow keys move within the group |
| Select | yes | `select` | `combobox` | `aria-expanded`, `aria-controls` | the arrows open it and move within it; `Esc` closes it |
| Tooltip | no | — | `tooltip` | `aria-describedby` | `Esc` dismisses it |
| Toast | no | — | `status` | `aria-live` | — |
| Tabs | yes | — | `tablist` | `aria-selected`, `aria-controls` | the arrow keys move between tabs |
| Link | yes | `a` | `link` | `tabindex` | `Enter` follows it |
| Avatar | no | `img` | `img` | `alt` | — |
| Progress | no | — | `progressbar` | `aria-valuenow`, `aria-valuemin`, `aria-valuemax` | — |

### How a row is checked

The subject is the markup the component was adopted into — the same `applied:`
reading `refs/refine/coverage.md` grades files by, so there is one detector of
where a component lives.

**A native element carries its own semantics.** Markup that uses the row's
native element has met the role, and has met the attributes too: a real
`<input type="checkbox">` needs no `aria-checked`, and adding one is a way to
make it wrong. The attribute column is what an author owes when they write the
role by hand instead — `role="checkbox"` on a `<div>` promises a state, and
nothing carries it unless it is written.

| Reading | Reported as |
|---------|-------------|
| the markup uses the native element | met, natively |
| the markup writes `role="…"` and every attribute in the row | met, explicitly |
| the markup writes the role and misses an attribute | `aria-unmet`, an `error`, naming each missing attribute |
| the markup has neither the element nor the role | `aria-unmet`, an `error` |
| the component is not built, or its markup could not be read | `aria-unverified`, a `warn` — stated, not failed |
| the archetype's row states no role and no attributes | **no expectation recorded**, and the component is neither passed nor failed on it |

The last two rows are the honesty in this section. A `Card` has no ARIA
expectation because a surface with content on it is not a widget, and the result
says exactly that rather than showing a green tick that would imply a check
happened. An unreadable source is a fact about the reading, not about the
component — the same rule that makes an unbuilt component `not built` in
coverage rather than `pass`.

The keyboard column is never checked. It is carried into the result so a person
reading the section knows what correct use requires, and it is labelled as
stated rather than verified.

## 4. The rules, and why each severity is what it is

<!-- phyllum:a11y-rules -->

| Rule | Severity | Detects |
|------|----------|---------|
| contrast-fail | error | a pair a component spec binds whose recorded colours fall below the ratio its context requires |
| focus-missing | error | an interactive archetype whose spec records no focus treatment — no `focus` state, and no `focus-ring` slot |
| aria-unmet | error | built markup that carries neither the archetype's native element nor its role, or writes the role and misses a required attribute |
| unpaired-token | warn | recorded colour tokens no component spec binds to a partner, so nothing says what they are read against |
| unreadable-pair | warn | a bound slot that is not a colour Phyllum can read, or a pair with a translucent side |
| aria-unverified | warn | an archetype with an expectation whose component is unbuilt or whose markup could not be read |

The split is the one the whole stage runs on: **an `error` is a fact about the
component, a `warn` is a fact about what could be read.**

The three errors are all statements the design system made about itself and then
broke. A recorded pair below its threshold is a measurement, not an opinion. A
missing focus treatment is an absence in a file Phyllum owns. Markup with no
role and no native element is text that was read and did not contain them.

The three warnings are all limits of the reading. An unpaired token might be a
theme colour, a chart series or a mistake, and this section will not guess
which. A translucent pair has an answer that depends on a backdrop nothing
records. An unverified expectation is one whose source was never opened. None of
them fails the section, and each of them is printed, because the one answer a
gate may not give is silence.

### The section verdict

A component passes a11y when it carries **no error finding**, and the section
passes when every component that could be checked passes. A component whose
archetype the contract table does not name is not graded — a `custom` component
claimed no contract, so there is no row to hold it to, and it is reported that
way rather than passed.
